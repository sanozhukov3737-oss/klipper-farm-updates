# Процесс релиза

Короткое описание того, как устроены номера, имена файлов и публикация. Написано после
релиза 1.15.2, где пришлось разбираться с двумя ловушками: релиз R152 собран из оверлеев
r152…r155, а заметки к опубликованному релизу лежали в файле `r155-release-notes.md`.

## Два разных вида заметок

| Файл | Что описывает | Кому |
|---|---|---|
| `rNNN-release-notes.md` | **оверлей** — набор изменений в исходниках | разработчику |
| `rNNN-ota-release-notes.md` | **опубликованный релиз** — что получит пользователь | пользователю, попадает в `update-v20.json` |

Это разные документы, и они не обязаны совпадать. Оверлей r152 — про надёжный запуск
демона; опубликованный релиз R152 — про данные на диске D, конец печати без ложной
ошибки, окно старта демона и честную версию.

Опубликованные заметки называются **строго по тегу** релиза: тег `r152-ota` →
`r152-ota-release-notes.md`. Никогда по номеру последнего оверлея.

## Правило нумерации

> **Один релиз = один sequence = один тег `rNNN-ota`.**

- `sequence` в `update-v20.json` равен числу в теге и в имени заметок.
- `sequence` строго возрастает на единицу: 151 → 152 → 153.
- Повторно использовать sequence нельзя. Апдейтер предлагает обновление только при
  `manifest.sequence > installedSequence`, а при равном sequence с другим содержимым
  отклоняет манифест как подмену (`Equivocation` в `kf-update`).

Если в репозитории накопились оверлеи, которые ещё не выпускались, номер релиза
не совпадёт с номерами оверлеев — это нормально. Но тогда перед сборкой нужен оверлей,
который поднимает `UPDATE-CHANNEL.json` до нового sequence и меняет
`RELEASE-BUILD-ID.txt` на `V20.6-R15.<N>-…`. Именно так появился `r155-release-sequence`:
оверлеи r152–r154 были уже применены, а sequence оставался 151.

## Порядок выпуска

1. Оверлеи применяются цепочкой в `preview10-natural-understanding.yml`.
2. `version-stamp/stamp-version.py` проставляет версию из `version-stamp/version.json`.
3. Прогон CI собирает установщик, runtime и evidence.
4. Runtime публикуется workflow `publish-update-runtime.yml`.
5. Релиз выпускается `publish-release.mjs`:

```bash
node publish-release.mjs \
  --run-id <ID принятого прогона> --head-sha <полный SHA> \
  --sequence <N> --version <X.Y.Z-rN> \
  --installer <путь к setup.exe> --notes r<N>-ota-release-notes.md \
  --dry-run
```

`--dry-run` делает все проверки и ничего не пишет. Без него скрипт создаёт draft,
заливает ассеты, сверяет их контрольные суммы и только потом публикует.

6. Манифест подписывается только через `sign-update.mjs`:

```bash
KF_PUBLISHER_KEY_PATH=D:\kf-secrets\KF-PUBLISHER-PRIVATE.pem \
node sign-update.mjs --sequence <N> --version <X.Y.Z-rN> \
  --sha256 <sha256 setup.exe> --bytes <размер> --notes r<N>-ota-release-notes.md
```

`publish-release.mjs` вызывает его сам.

## Ключ подписи

Хранится только в `D:\kf-secrets\KF-PUBLISHER-PRIVATE.pem`. Права: владелец, SYSTEM,
Администраторы. В репозиторий не попадает, в рабочую директорию задачи не копируется.
Публичная половина — в `UPDATE-CHANNEL.json` (`publicKeyHex`); `sign-update.mjs` читает
её оттуда и отказывается подписывать ключом, которому клиенты не доверяют.

## Что проверяет публикация

`publish-release.mjs` отказывается продолжать, если:

- прогон не является успешным прогоном Windows-приёмки этого репозитория и коммита;
- provenance собран другим прогоном, другим коммитом или с неполными флагами приёмки;
- байты установщика не совпадают с принятыми;
- runtime с тем же дайджестом ещё не опубликован;
- новый sequence не больше опубликованного.

Последний пункт появился именно из-за случая с 1.15.2: релиз мог уйти в пустоту,
потому что sequence не подняли.
