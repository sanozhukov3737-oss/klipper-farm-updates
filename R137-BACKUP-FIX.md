# R137 — исправление накопления резервных копий

Исправление подготовлено на точных исходниках опубликованного R136 и проверено на Windows: 214 тестов прошли, ошибок нет, два прежних теста остаются пропущенными. Установщик R137 не собран, штатный канал обновлений остаётся R136.

Пользователь самостоятельно удаляет прежние резервные копии. Эта работа исправляет механизм приложения; действий с файлами на пользовательском компьютере не выполнялось.

## Найденная причина

В R136 координатор при каждом запуске задавал `last_backup = Instant::now() - BACKUP_INTERVAL`: первая итерация снова создавала полную копию, даже если предыдущая была сделана несколько минут назад. При ошибке другой части итерации этот же таймер всё равно откладывал попытку на сутки.

Ограничение в семь готовых файлов `farm-v20-*.sqlite3` уже существовало. Оно не охватывало временные `.farm-v20-*.partial`, `.drill-*.restore.partial` и их SQLite-спутники `-wal`, `-shm`, `-journal`. Guard удалял только основной временный файл, а после остановки процесса guard вообще не выполняется. Поэтому временные остатки могли накапливаться сверх семи готовых копий.

Дополнительно открытие источника через `Connection::open` позволяло создать пустую рабочую базу, если исходный файл исчез. Новая логика открывает существующую базу только для чтения и проверяет схему до публикации и ротации копий.

## Изменение поведения

- Сохраняются прежние правила: автоматическая копия раз в 24 часа и максимум семь готовых копий; ручное резервирование остаётся доступным.
- Срок следующего автоматического резервирования определяется готовыми копиями на диске и переживает перезапуск. Проверка срока выполняется раз в минуту и читает только заголовок и метаданные SQLite, без полного сканирования большой базы.
- Создание, проверка срока, пробное восстановление и очистка используют общий mutex. Одновременные автоматические вызовы не создают повторные полные копии.
- Очистка распознаёт только собственные временные имена приложения, включая отдельные спутники без основного файла. Она работает в самой папке `backups`, поддерживает перенаправление каталога через Windows Junction и не проходит по вложенным каталогам или ссылкам на отдельные файлы.
- Временные SQLite-файлы удаляются после закрытия дескрипторов при успехе и ошибке; остатки прерванной операции убираются при следующем запуске и штатном обслуживании.

Изменяются только `src-tauri/src/transactional_core/backup.rs` и `src-tauri/src/transactional_core/farm_coordinator.rs`. Данные принтеров, пластика и настройки не меняются. Без пользовательской базы нельзя подтвердить, какая часть её 600–700 МБ занята данными, а какая свободными страницами; эта работа не удаляет строки базы ради уменьшения размера.

## Проверка и продолжение

`r137-backup-patch.json` и `.sha256` содержат два изменения и полный hash-инвентарь 1786 файлов R136. `apply-r137.py` восстанавливает точную базу и проверяет все остальные байты. `r137-required-tests.json` перечисляет обязательные новые регрессии и ожидаемое количество нативных тестов.

Проверка настоящего кода приложения на Windows завершилась успешно: [run 39969972439](https://github.com/sanozhukov3737-oss/klipper-farm-updates/actions/runs/39969972439), commit `0d9b0f149d93710414eef9e0c055f5733fc1db5e`.

- Основной набор: 214 passed / 0 failed / 2 ignored. Новых пропущенных тестов нет.
- Прошли все 11 новых сценариев резервирования, включая перезапуски, одновременные запросы, остатки временных файлов, Windows Junction и продолжение ротации после заблокированного файла.
- Прошли четыре существующие сетевые регрессии отправки на печать.
- До и после нативной проверки сверены все 1786 исходных файлов: изменены только два согласованных файла, остальные байты сохранены, лишних файлов нет.

В первой проверке один новый тест неверно предполагал, что Windows-атрибут read-only запретит удаление. Проверка исправлена: файл удерживается открытым без `FILE_SHARE_DELETE`, создавая настоящую блокировку удаления. Рабочий код между двумя проверками не менялся; повторная проверка прошла полностью.

Полный исходный артефакт CI сохранён как `r137-native-evidence.zip`, его SHA256 — в `r137-native-evidence.sha256`. `r137-native-verification.json` связывает итог с commit, run, artifact, SHA256 патча и фактическими журналами тестов. SHA256 патча: `3a78d401483a3ab5b0c6f9f9f3262bc12ebbfb019551a9bf49b83c9c5dfc20d5`.

Этот этап проверяет исходники и не создаёт установщик, не меняет идентификатор установленной версии и не публикует обновление. Для доставки исправления в приложение требуется следующий этап — сборка и публикация R137.
